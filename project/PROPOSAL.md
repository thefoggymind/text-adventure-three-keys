## 選定理由

### なぜ実績システムか

| 観点 | 評価 |
|------|------|
| **工数** | 既存コードへの追加で完結。新規プロジェクトより圧倒的に小さい |
| **ユーザー定着** | 全6エンディングのコンプリート意欲を刺激し、リプレイ率向上 |
| **SNSシェア促進** | 実績解除時のシェアボタンで拡散期待。実績100%達成通知で更なるシェア |
| **収益化貢献** | 間接的: プレイ時間増→寄付率向上。直接的: 実績解除でKo-fi誘導 |
| **技術的リスク** | LocalStorageのみで完結。サーバーサイド不要、API費用ゼロ |

### 他の候補との比較

| 候補 | 工数 | ユーザー影響 | 収益化 | リスク |
|------|------|-------------|--------|--------|
| **実績システム** | 小（3〜5日） | 高（リプレイ性） | 中（間接的） | 低 |
| BGM/SE追加 | 中（5〜7日） | 中（没入感） | 低 | 中（ライセンス） |
| Steam配信準備 | 大（2〜3週間） | 高（新市場） | 高（販売） | 高（審査・コスト） |
| 英語版ローカライズ | 中（1週間） | 中（市場拡大） | 中 | 中（翻訳品質） |

### 現在の資産活用

| 資産 | 活用方法 |
|------|---------|
| renderer.js の getAchievements/recordEnding | 既存の実績管理関数を拡張 |
| localStorage 保存処理 | 実績データの永続化にそのまま流用 |
| game.test.js 49テスト + renderer.test.js 57テスト | リグレッションテストとして活用 |
| 実績解除UI（showNotification） | 実績解除ポップアップに流用 |
| ending-count / progress-fill / progress-percent | 進行度表示の強化に活用 |

## 概要

「3つの鍵 — Web Edition」に**実績システム（Achievement System）**を追加する。
現在の `getAchievements()` / `recordEnding()` は内部カウントのみ行っているが、これを拡張し、
**個別実績の定義・解除・表示・通知**を行うフル機能の実績システムにアップグレードする。

### 実装範囲

| 区分 | 内容 |
|------|------|
| **実績定義** | 10〜15個の実績を定義（エンディング到達、アイテム収集、プレイ回数、隠し要素） |
| **解除検出** | ゲーム内イベント（ENDING_REACHED, ITEM_FOUND, PLAY_COUNT）を監視し条件一致で解除 |
| **解除通知** | 実績解除時に画面上部にポップアップ表示（showNotification拡張） |
| **実績一覧画面** | タイトル画面からアクセス可能な実績一覧（達成済み/未達成） |
| **進行度表示** | 現在のending-count / progress-fillを活用し、総合達成率％を表示 |
| **SNSシェア** | 全実績達成時に「全実績コンプリート！」シェアボタン表示 |

### 実績案（全12個）

| # | 実績名 | 解除条件 | 非表示 |
|---|--------|---------|--------|
| 1 | はじまりの一歩 | 初めてゲームを開始する | — |
| 2 | 左の道を行く | 左の道を選択する | — |
| 3 | 右の道を行く | 右の道を選択する | — |
| 4 | 栄光の勝利 | いずれかのエンディングで勝利する | — |

| 6 | 帰還 | 中立エンディング「帰還」に到達 | — |
| 7 | 真の英雄 | 隠しエンディング「真の英雄」に到達 | ○ |
| 8 | 収集家 | 全アイテムを収集する | — |
| 9 | 探検家 | 全6エンディングをコンプリート | ○ |

## 技術スタック

| レイヤー | 技術 | 備考 |
|---------|------|------|
| 実績データ | localStorage（JSON） | 既存のセーブ/実績保存機構を拡張 |
| 実績定義 | game.js に定数として定義 | 条件ロジックはgame.js、UIはrenderer.js |
| 実績通知 | renderer.js (showNotification拡張) | 既存トースト通知を実績用にブラッシュアップ |
| 実績一覧画面 | HTML + CSS（新規画面追加 or モーダル） | index.htmlに実績一覧用の画面を追加 |
| テスト | Jest（既存フレームワーク） | 既存106テスト + 新規実績テストを追加 |
| ホスティング | GitHub Pages（変更なし） | サーバーサイド不要のまま |

## 期待効果

### 定量効果

| 指標 | 現状 | 期待値 | 根拠 |
|------|------|--------|------|
| リプレイ率（2回以上） | 推定30% | 60%以上 | 実績コンプリート目的の再プレイ |
| 平均プレイ時間 | 推定15分 | 30分以上 | 全実績達成までの試行錯誤 |

| Ko-fi寄付率 | 推定1% | 3〜5% | プレイ時間増×感情移入向上 |

### 定性効果

- **ユーザー体験の向上**: プレイの目的が「クリア」から「コンプリート」に拡張
- **コミュニティ形成**: 実績共有によるSNSでの話題作り
- **継続的改善の基盤**: イベント駆動型の実績システムは今後の機能追加（デイリーチャレンジ等）にも拡張可能

## リスク評価

| リスク | 確率 | 影響 | 対策 |
|--------|------|------|------|
| localStorage容量超過 | 低 | 低 | 実績データは数KB未満。現状のセーブデータと合わせても余裕 |
| 既存テストの破壊 | 低 | 高 | 実績ロジックは既存コードに影響しない設計（イベントフック方式） |
| 実績バグによるセーブ破損 | 低 | 中 | 実績データとセーブデータは別キーで保存。片方の破損が他方に影響しない |
| 実績が少なすぎて物足りない | 中 | 低 | 12個は業界平均（8〜15個）の範囲内。Phase2で追加可能 |

## 結論

**「実績システム追加」** は、現在のWeb版に最小工数で最大の付加価値を追加できる最適な次プロジェクトである。

- ✅ 既存コード（renderer.jsのgetAchievements/recordEnding）を拡張するだけ
- ✅ 既存106テストを壊さずに追加可能（イベントフック方式）
- ✅ リプレイ率・プレイ時間・SNSシェアの向上が期待できる
- ✅ サーバーサイド不要、追加コスト0円
- ✅ 4〜6日で完了可能（現在の工数見積もり内）
